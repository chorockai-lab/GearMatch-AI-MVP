# ITEMS 콜드 스타트 — 가상 러너 Seed · 자동 확장 · 대체 탐색

> **완료** — PR #33 main 병합(`9250279`), DB 함수·가상 Seed 운영 적용, Production QA 통과(2026-10-19, §8). 목표: 실제 러너 데이터가 없거나 부족해도 ITEMS가 "결과 없음"으로 끝나지 않고 러닝화를 탐색할 수 있게 함.

## 1. 결과 우선순위 (`public.items_match()` = `src/lib/items/aggregate.ts` `itemsMatch()`)

| 순서 | 상태 | 대상 | 화면 |
|---|---|---|---|
| 1 | `real` · base | 실제 러너(`data_source` = survey/partner/internal) ±5cm·±5kg·±10mm·같은 거리, 5명 이상 | 기존 Runners Like You — 실제 인원·비율 |
| 2 | `real` · wide | 같은 조건 ±10·±10·±20 (자동) | 위 + "조금 더 넓은 조건에서 찾았어요." |
| 3 | `example` · base | 가상 Seed(`demo`)만, 기본 범위, 5명 이상 | "나와 비슷한 조건에서 살펴볼 러닝화" + `예시 데이터` + 안내문, **숫자·순위·막대·누적 없음**, 이름순 |
| 4 | `example` · wide | 가상 Seed만, 확장 범위 | 위 + 넓힌 조건 안내 |
| 5 | `browse` | 활성 상품 전체(신체 정보 미입력 포함) | "아직 비슷한 조건의 러너 정보가 충분하지 않아요." + "러닝화 둘러보기"(숫자 없음) |

- 단계는 **상품이 1개 이상 나올 때만** 사용하고, 아니면 다음 단계로 넘어갑니다.
- 실제 러너와 가상 Seed는 어떤 단계에서도 같은 집계에 들어가지 않습니다(SQL `where (data_source = 'demo') = is_demo`).
- 사용자 본인의 `runner_profiles`는 **매칭 기준값으로만** 쓰이며, 누구의 집계에도 포함되지 않습니다(이전과 동일).
- 기존 `runners_like_you()`는 남겨 두되 가상 Seed를 무시하도록 바꿨습니다(이전 버전 앱이 Seed를 실제처럼 세지 않게).
- "조건이 가까운 러너까지 보기" 버튼은 자동 확장으로 대체. 예전 `/items?range=wide` 링크도 같은 화면을 엽니다.

**실제 러너 데이터(`survey`/`partner`/`internal`)의 조건**: 실제 사람의 신체 정보·착용 신발을 본인 동의 등 적법한 근거로 받은 경우에만 넣습니다(기존 `items:import`, `demo`는 거부). 현재 Production에는 0명입니다.

시험 사용자는 Seed의 난수와 **별도로** 뽑은 여러 시나리오입니다. base = 기본 범위에서 찾음, auto = 기본 또는 자동 확장에서 찾음, shown = 어떤 목록이든 표시(대체 탐색 포함).

|---|---|---|---|---|

| S2 BMI −1.5(러너가 더 마른 경우) | 4,000 | 62.9% | 95.9% | 100% |
| S3 BMI +2.0 | 4,000 | 64.2% | 94.2% | 100% |
| S4 발 사이즈 ±12mm 이탈 | 4,000 | 42.7% | 94.9% | 100% |

| S6 키 145~195 × BMI 17~33 균등 격자(분포 무시) | 792 | 24.7% | 64.5% | 100% |

구간별(S1+S2, base / auto): 키 ≥185 0% / 34.7% · 175~184 46.0% / 93.2% · <155 43.5% / 93.4% · BMI <18.5 12.7% / 80.5% · BMI ≥30 3.9% / 64.0% · 발이 키 대비 ±15mm 이상 30.1% / 91.6% · 남 62.2% / 95.5% · 여 68.1% / 97.2% · 거리 구간 63~68% / 95~98%.
신체 정보 미입력(4종 각각) → `browse` 50개, 숫자 없음. 매칭 그룹에 활성 상품이 없을 때 → `browse` 50개.
분리 확인: 가상 Seed 300명 옆에 실제 러너 6명을 두면 결과는 `real` 6명이며 가상 Seed는 집계에서 빠짐.

**반복성(같은 사용자 2,000명, 러너 시드 30개)**: 120명 base 평균 17.4%(11.2~23.3) · auto 86.5%(83.4~89.6) / 300명 base 평균 67.0%(63.9~69.6) · auto 97.2%(96.3~97.9).

**이전 120명 보고 정정**: 본문 "기본 23.3% · 확장 87.8%"는 시드 20261016 한 번의 결과였고, 30개 시드 중 **가장 높은 값**이었습니다. 함께 적은 "다른 시드 5개 범위(14.6~19.9%)"에는 이 값이 포함되지 않아 본문과 범위가 어긋났습니다. 대표값은 평균 17.4%(범위 11.2~23.3%)로 정정합니다.

## 4. 화면 (기존 레이아웃 유지, 필요한 부분만)

- `ItemsMain`: 위 표의 상태별 분기. 실제 목록·카드는 그대로. 예시/탐색은 숫자 없는 행(브랜드·용도·모델·저장).
- `ProductDetail`: 같은 `items_match()` 결과 사용 → 실제일 때만 비율·"N명 중 X명"·HOW THEY RUN. 예시는 `예시 데이터` + 안내문, 탐색은 "아직 비슷한 조건의 러너 정보가 충분하지 않아요." 상세에서 저장 그대로.
- 문구 규칙(`src/lib/items/view.ts`, 자동 테스트): 예시 안내 "한국인 신체 통계를 참고해 구성한 가상 러너 기반의 예시입니다. 실제 러너의 착용 기록이나 추천 결과는 아닙니다." · 적합성·만족도·인기 표현 금지.
- 분석 이벤트: `items_view`·`shoe_detail_view`의 `status`가 `real`/`example`/`browse`, `range`가 `base`/`wide`/null. 이벤트 이름·속성 이름은 그대로(기존 지표 유지; `shoe_detail_view`에 `status` 속성 추가 — PostHog 허용 목록에 이미 있음).

## 5. Production 적용 (승인 후, 순서 중요)

1. **DB 함수**: SQL Editor에 `supabase/migrations/20261017000000_items_match.sql` 실행 — `items_match()` 추가, `runners_like_you()`가 demo를 무시하도록 교체. 기존 행 변경 없음. 확인: `select proname, pronargs, prosecdef, has_function_privilege('anon','public.items_match()','execute') from pg_proc where proname = 'items_match';` → `0 · true · false`
2. **앱 배포**(PR 병합) — 이 시점부터 ITEMS는 실제 러너 0명이므로 `browse`(전체 상품 탐색)로 동작
3. **가상 Seed 입력**: 로컬에서 `npm run items:seed -- --sql supabase/seed/items.demo-seed.sql` → SQL Editor 실행(트랜잭션). `demo` 행만 지우고 300명·441건 입력, 실제 행은 건드리지 않음. 확인: `select data_source, count(*) from public.seed_runners group by 1;`
4. Production에서 `?qa=1` 계정으로 상태별 확인

**순서 이유**: 함수 없이 앱을 먼저 배포하면 ITEMS가 오류. Seed를 먼저 넣으면 이전 앱이 쓰던 함수는 이미 demo를 무시하므로 영향 없음(1번에서 교체).
**Preview**: Preview와 Production이 같은 DB를 쓰므로 Preview 확인도 1번 이후에만 가능. Seed는 Preview 검증 목적으로 넣지 않습니다.
